# 검증 전략

상태: 구현 후 수행할 계획. 이 문서는 테스트 실행 결과가 아니다.

## 1. 지원 범위와 시험 조건

| 구분 | 최초 지원 | 확인 조건 |
| --- | --- | --- |
| Windows | Windows 11 25H2 이상 x64 | 최소 25H2와 릴리스 시점 최신 안정 일반 채널, WebView2 버전 기록 |
| macOS | macOS 15 이상 Apple Silicon | 최소 지원 OS와 최신 안정 OS, 실제 arm64 실행 |
| macOS Intel | 후속 지원 후보 | x64 빌드·패키징·실제 Intel 실행 통과 후 지원표에 추가 |
| Windows ARM64 / Linux | 초기 범위 밖 | 빌드 결과만으로 지원을 표기하지 않음 |

OS 하한은 [ADR 0002](decisions/0002-runtime-and-builder-contracts.md)의 v1 결정이다. 현재 개발 환경의 부분 기록은 [개발 검증 기록](validation/2026-11-07-development.md)에 둔다. 지원 OS의 입력·WebView·외부 설치 전체 시험은 미실시이며 최소 지원과 최신 안정 OS를 모두 시험한다. VM·CI는 권한·전력·고DPI·실제 설치를 모두 대체하지 않는다. 릴리스가 진행돼도 OS 하한·target 변경은 관련 ADR·빌드 설정과 함께 한다.

## 2. 테스트 계층

| 계층 | 검증할 내용 |
| --- | --- |
| Rust 단위 | 프로젝트·경로·프레임·loop 검증, 입력 정규화, priority/동률/쿨다운/중단, 모의 시계 종료, held·KPS·두벌식 변환·KMP·reset |
| Runtime 통합 | 모의 입력부터 상태·위치·렌더 snapshot까지, 채널 재연결, 저장 실패 복구 |
| 렌더러 | 시트 프레임·anchor·배율·수평 반전, DPR, 유휴 재그리기 중단 |
| Builder 통합 | 배포 CLI·팩만으로 두 프로젝트 빌드, snapshot 변경 감지·최종 검증·hash·팩 무결성, 취소·캐시·target·identity |
| OS 수동/통합 | 실제 전역 입력, 클릭 통과, 포커스, 트레이, 권한, 다중 모니터, 절전 |
| 배포 | 실제 다운로드한 설치 파일을 제작 도구 없는 다른 컴퓨터에서 설치·실행 |
| 보안 계약 | overlay의 설정/Builder/mock 명령 거부, release CSP·자산 scope·원격 탐색 차단, 입력 이력 부재 |

구현 세부사항을 그대로 복제한 테스트보다 사용자에게 보이는 실패를 검증한다. 전역 키를 실제로 발생시키는 테스트는 전용 테스트 세션에서만 실행하고 일반 개발자의 작업 입력을 방해하지 않는다.

## 3. 프로젝트·빌드 시나리오

1. **서로 다른 앱**: typing-cat과 click-mascot 프로젝트에서 이름·아이콘·identifier·이미지·bindings를 다르게 지정한다. 공통 코드 수정 없이 각각 빌드한다.
2. **독립 실행**: 원본 프로젝트가 없는 컴퓨터에서 두 앱을 실행한다. Node·Rust·Studio 설치 여부에 영향을 받지 않는다.
3. **격리**: A의 위치·배율 변경, A 제거, A 업데이트가 B의 실행·설정에 영향을 주지 않는다.
4. **동시 실행**: 두 앱이 키/마우스를 함께 관찰한다. 한 앱의 단일 인스턴스 잠금이 다른 앱을 막지 않는다.
5. **리소스 반영**: 이미지나 매핑을 바꿔 재빌드하면 생성 앱이 변경된 리소스를 사용한다. 캐시가 예전 자산을 섞지 않는다.
6. **검증 실패**: 미래 스키마, 누락 PNG, 프레임 범위 초과, 알 수 없는 키, 경로 탈출, symlink 탈출, 초대형 이미지가 빌드 전에 차단된다.
7. **취소·실패**: 컴파일·패키징 중 취소, 도구체인 누락, 디스크 부족에서 기존 프로젝트·성공 산출물을 유지한다.
8. **플랫폼**: 다른 OS용 로컬 빌드를 지원한다고 잘못 표시하지 않는다. target별 파일·아키텍처와 보고서가 일치한다.
9. **Builder 자체 배포**: 원래 저장소 없는 별도 제작 환경에 OS별 CLI·팩·도구체인만 두고 doctor→두 앱 build를 통과한다. 작업 디렉토리 밖 source path 참조·팩 변조·호환 버전 불일치는 실패한다.
10. **snapshot**: 사전 검사~복사 중 JSON·PNG·symlink를 변경하면 실패한다. 최종 검증 후 원본을 이동·수정해도 확정 snapshot만 빌드한다. 실제 사용 파일 hash와 보고서가 일치한다.
11. **업데이트 identity**: 같은 identifier·slug에서 product.name·버전·기본값을 바꿔 업데이트해 설치/제거 항목이 중복되지 않고 명시한 사용자 값이 보존된다. 별도 identifier의 앱과 설치·제거·설정을 격리한다.
12. **산출물**: 설치 파일·안내·SHA256SUMS·보고서·라이선스가 포함되고 정적 검사와 외부 실행 여부를 구분한다. 같은 버전 재빌드가 이전 성공 파일을 덮어쓰지 않는다.

## 4. 입력과 오버레이 시나리오

- 다른 텍스트 편집기에서 한글 IME·영문·한영 전환·modifier 조합을 사용하면서 애니메이션을 확인한다. 문자 내용을 저장하지 않는다.
- 같은 키 누르기/유지/떼기, 여러 키, 반대 방향, 빠른 반복, 긴 key hold를 검사한다.
- 키 감지가 원래 앱의 텍스트 입력·단축키를 차단하지 않는다. 전역 조합키 충돌은 실패 결과로 설명한다.
- 마우스 이동·각 버튼·휠과 고폴링 장치에서 클릭 누락·정체가 없는지 확인한다.
- 버디의 보이는 부분을 즉시 드래그할 수 있고 놓으면 위치가 저장된다. 투명 여백과 실루엣 내부의 투명 부분에서 뒤쪽 앱을 클릭할 수 있는지, 드래그 중 투명 부분을 지나도 놓기까지 이어지는지 검사한다. 화면 가장자리에서 투명 여백을 밖으로 넘겨 놓고 재시작해 위치가 유지되는지 확인한다.
- 표시·숨김·설정 열기·편집 완료 후 전경 앱의 포커스가 불필요하게 바뀌지 않는다.
- 단일/다중 모니터, 보조 화면의 음수 좌표, Windows 100/150/200% 혼합 배율, Retina 배율을 검사한다.
- 모니터 제거·주 모니터 변경·배율 변경 시 캐릭터가 보이는 영역으로 복구된다.
- 잠금·절전·프로세스 재시작·입력 어댑터 재연결 뒤 held 상태가 남지 않는다.
- 권한 거부·철회·부분 수신에서 캐릭터와 트레이를 조작할 수 있고 재시도할 수 있다.
- 다른 일반 앱(텍스트 편집기·브라우저·업무 앱)을 전경으로 두고 캐릭터 앱 포커스 없이 키·속도·키워드 반응을 검사한다. 원래 입력·단축키·텍스트 선택이 유지돼야 한다.
- 일회성 loop 참조 거부, 같은 priority의 현재/새 binding 순서, restart/ignore, 버린 입력의 쿨다운 비소비, 중단 반응 폐기·완료 후 기본 상태 복귀를 검사한다.
- 이동+walk, 이동 중 jump, 속도 애니메이션+이동, 반대 키 상쇄, 화면 경계에서 walk 중지, 커서가 정지한 채 캐릭터만 이동할 때 방향을 검사한다.
- KPS 창·0.5/3.0 경계·기본 50/100/250 ms와 사용자 지정 타이밍, 구간 겹침 거부, repeat/modifier 제외, 최대 집계 reset을 모의 시계와 실기 양쪽에서 검사한다.
- 한글 초성·중성·종성의 변환표 전체, 쌍자음 Shift·복합모음·겹받침·영문 대소문자·직접 steps 동등성·지원하지 않는 문자 거부를 fixture로 검증한다. `고양이`의 두벌식 steps는 rhdiddl이다.
- keyword 최종 키가 특정 키·wildcard와 겹치는 경우 하나의 후보만 실행한다. KMP 겹침·불일치·Shift 오류·timeout·Backspace·Control 조합·마우스 클릭 reset을 검사한다. 실제 IME 한/영 모드를 바꿔도 같은 물리 순서가 발동해야 한다.
- 키를 누른 채 키보드 제거, 두 키보드의 같은 키·하나만 release, macOS 세션 통합 상태 대조·보안 입력·조회 실패를 검사한다. 장치별 보장이 없는 플랫폼의 한계를 시험 보고서에 구분한다.
- 편집/설정/숨김/전체 일시 정지 동안 반응·속도·sequence가 중지된다. 재개 시 사용자 토글은 보존하고 이전 held·큐·prefix·속도는 되살아나지 않는다. 현재 눌린 키의 repeat만으로 이동하지 않는다.
- 편집 완료는 새 기본 배치를 저장하고 취소는 진입 직전 위치·배율로 복원한다. 자동 이동 후 재시작은 기본 배치이며 tick마다 디스크 쓰기를 하지 않는다.
- 설정 손상·백업 손상·미래 버전·쓰기 실패·중간 종료에서 원본 보존·복구 안내·입력 off·미저장 상태를 검사한다. 위치만 초기화와 전체 초기화의 입력 토글 차이를 검사한다.
- 작업 표시줄·Alt-Tab·Dock·Space 정책과 트레이 복구를 검사한다. 전체 화면·보안 화면 위 표시를 보장한 것으로 보고하지 않는다.

## 5. 서명·설치·권한 시나리오

**기본 빌드에서 공식 인증서·Apple 계정·공증 자격증명 없이 산출물이 만들어져야 한다.**

| 대상 | 검증 |
| --- | --- |
| Windows 기본 | 미서명 사용자 단위 설치, 제거·재설치, 다운로드 시 신뢰 경고의 실제 동작 |
| Windows 셀프 서명 | 선택한 로컬 identity 사용, identity 누락 실패, 공식 신뢰로 잘못 표시하지 않음 |
| macOS 기본 | ad-hoc 서명 구조 확인, 실제 다운로드 후 OS 실행 승인, 설치된 경로에서 재실행 |
| macOS 권한 | 입력 모니터링 거부·허용·철회·재빌드/업데이트 후 재점검 |
| 공통 | OS 실행 승인을 입력 권한 허용으로 취급하지 않음, 자동 신뢰 루트 등록 없음 |
| 제한 환경 | 조직 정책·Smart App Control 등으로 승인 선택이 없는 경우 지원 제한과 원인을 기록 |

OS별 근거와 사용자 흐름은 [빌드·배포](build-and-distribution.md)를 따른다. 같은 제작 컴퓨터에서 실행한 결과로 배포 검증을 통과시키지 않는다.

## 6. 성능 측정 방법

### 조건

Release 빌드, 디버거·개발 서버 없음, 기본 256px 캐릭터, 설정 창 닫힘, 모니터 60Hz/고주사율을 각각 기록한다. OS·CPU·메모리·배율·WebView·전원 상태·프로젝트 hash를 남긴다. 기준은 Windows 4코어/8GB 이상 실기와 Apple Silicon M1/8GB급 실기로 하고 실제 기기명을 M0 기록에 고정한다.

워밍업 60초 후 5분씩 3회 측정하고 중앙값과 최악값을 보고한다. 비교 대상은 앱 종료, 정적 유휴, 기본 idle 애니메이션, 타이핑/클릭 30 FPS, 숨김, Studio 미리보기 종료 후 상태다. 애니메이션이 있는 idle을 무재그리기 유휴와 섞지 않는다.

필수 측정은 1개와 서로 다른 2개 앱에서 수행한다. 두 앱 모두 활성인 조건과 하나만 활성인 조건을 포함하며 각 앱 N01~N04 및 합계 자원·전력을 보고한다. 메모리 합계 목표는 400 MiB, 유휴 CPU 합계 2%/활성 합계 10% 이하다. 시작 시간은 두 앱 동시 시작, 입력 지연은 둘 모두 수신하는 조건에서도 측정한다. 5개 앱은 확대 측정으로 결과를 기록하되 P0 지원 약속으로 사용하지 않는다.

### 지표

- 메모리: Windows는 프로세스 트리의 private working set, macOS는 귀속 가능한 physical footprint를 사용한다. 공용 WebView 프로세스의 귀속 한계를 보고하고 숫자를 OS 간 직접 비교하지 않는다.
- CPU: 1개 논리 코어를 100%로 정규화한다. 시스템 전체 CPU%와 혼동하지 않는다.
- GPU·전력: 앱 종료 기준과 투명/불투명/숨김 조건을 비교한다. 단순 CPU 목표 통과만으로 저전력이라고 결론내리지 않는다.
- 입력: native callback 진입 시각부터 렌더러의 다음 프레임 처리 ACK가 돌아온 시각까지 측정한다. 같은 Rust 단조 시계로 큐 대기와 IPC 왕복 비용을 포함한다. 수신 복구로 합성한 해제 이벤트는 어댑터의 큐 등록 시각을 사용한다. 실제 화면 반영 지연이 필요하면 별도 영상/외부 측정을 사용한다.
- 위 입력 지연 표본은 30 FPS 시험팩에서 실제 시작한 일회성 반응이며 쿨다운·우선순위로 무시한 입력과 프레임 사이에 중단된 반응의 개수는 별도 집계한다. 표본 제외를 숨기지 않는다. 속도 구간 전환은 설정된 평가·안정화 정책 지연을 별도로 보고하고 80 ms 입력 목표와 섞지 않는다. keyword는 마지막 적격 down부터 반응 ACK까지 측정한다.
- 시작: 프로세스 시작부터 첫 캐릭터 프레임 ACK까지 측정한다. 내부 startupFrameMs는 Rust main 진입부터 창 표시 요청과 첫 정상 그리기 ACK 처리까지이며 OS 로더·main 이전 시간은 포함하지 않는다. N04 판정에는 외부 콜드 스타트 측정도 함께 필요하다. 오류 대체 그림을 정상 첫 표시로 인정하지 않는다. WebView 설치 시간과 앱 시작 시간을 분리한다.
- 빌드: 첫 의존성 다운로드, 첫 컴파일, 캐시 재빌드, 패키징 시간을 구분한다.

목표는 [N01~N04](product-requirements.md)의 200 MiB, 유휴 1%/활성 5%, p95 80ms, 2.5초다. 측정 결과를 바탕으로 유지하거나 근거와 함께 조정한다. 현재 달성 결과는 없다.

### 구현된 계측 사용법

`examples/performance-30fps`는 정적 idle 1프레임과 typing/typingFast·Space·클릭·고양이 키워드의 30 FPS 반응을 제공한다. 일회성 반응의 쿨다운은 0이며 restart다. 일반 샘플의 12/24 FPS 결과를 30 FPS 결과로 대체하지 않는다. 이 fixture는 시험용이며 제품 기본 동작을 변경하지 않는다.

1. 시험 앱의 설정에서 **반응 성능 진단 → 계측 초기화**를 누르고 설정 창을 닫는다. 설정을 열면 전역 감지가 중지되므로 실제 입력은 다른 앱을 전경으로 두고 수행한다.
2. 초기화 후 워밍업 60초 동안 모인 표본도 집계에 포함된다. 측정 구간만 비교하려면 워밍업 후 설정에서 다시 초기화하고 창을 닫아 5분 시험한다. 실제 유효 시간은 외부 타이머로 기록하고 설정 열기·닫기 시간과 구분한다.
3. 마지막 입력 반응이 끝난 뒤 5초 이상 기다려 ACK 미수신 유예를 마친다. 설정을 열어 **집계 새로고침**, **진단 JSON 저장**을 사용한다. 고정된 앱 데이터 폴더에 UUID 이름으로 저장하며 경로를 표시한다. trial마다 파일을 분리한다.
4. latency30Fps의 samples/p50Ms/p95Ms/maxMs/above2000Ms와 모든 제외·오류 카운터를 함께 보관한다. percentile은 nearest-rank다. p95Above2000Ms=true이면 p95Ms=null은 2000 ms 초과를 뜻하며, 표본 0의 null과 구별한다. 중단·오류·늦은 ACK 카운터는 서로 겹칠 수 있다. candidates는 cooldown/retrigger/same-input 억제/priority 거절/실제 시작으로 분해된다.
5. 추적 한도 초과·전송 실패·미수신·숨김 ACK 또는 미해결 pending이 있으면 해당 누락을 명시한다. 성공 표본 p95만으로 전체 반응이 통과했다고 판정하지 않는다. startupFrameMs는 초기화를 해도 유지되므로 콜드 스타트 trial은 앱을 완전히 종료하고 다시 실행한다.
6. JSON의 OS 종류/아키텍처·프로젝트 hash·빌드 모드·배율 외에 정확한 OS/WebView 버전·기기·주사율·전원·메모리·CPU·GPU·전력·외부 시작 시간을 별도 시험 기록에 채운다. 두 앱 시험은 서로 다른 projectId/identifier를 사용하고 각각의 JSON과 합계 자원을 보관한다.

자동 검증은 Rust의 지연 히스토그램·상관 ID·원문 없는 집계와 모의 Canvas/RAF의 ACK 시점·숨김·오류·동일 프레임 재시작까지다. 모의 Canvas 테스트가 실제 WebView 그리기·OS 입력·성능 목표를 통과했다는 뜻은 아니다.

## 8. 릴리스 종료 조건

필수 지원 플랫폼에서 P0 요구사항과 다운로드 배포 검증이 통과해야 한다. 설치·입력·설정 격리 실패는 출시 차단 이슈다. 실제 OS 권한·오버레이 테스트를 수행하지 못한 플랫폼은 미검증으로 남기고 정식 지원으로 광고하지 않는다.

M0는 최소 세로 경로 시험, M3는 P0 전체 종료다. 각 결과는 docs/validation에 OS·실제 버전·프로젝트/팩 hash·기기·요구사항 ID·통과/실패/미실시·재현 절차를 남긴다. 통제된 모의 입력 fixture는 보관하되 실제 작업 중 입력 이력은 수집하지 않는다. Markdown 링크·JSON 예시·요구사항 추적의 문서 정합 검사 통과를 실제 앱 시험 통과로 표시하지 않는다.
