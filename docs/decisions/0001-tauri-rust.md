# ADR 0001: Tauri + Rust 기반의 선언형 앱 빌더

- 날짜: 2026-11-07
- 상태: **Accepted — 제품 방향과 Tauri + Rust는 사용자 결정**
- 관련 문서: [기술 비교](../technology-evaluation.md), [아키텍처](../architecture.md)

## 배경

설정·리소스에서 서로 다른 독립 실행 데스크톱 캐릭터 앱을 만들어야 한다. 공통 요구는 전역 입력 관찰, 투명 오버레이, 위치·크기, 사용자 설정, Windows·Mac 빌드다. 공식 인증서 서명·공증은 필수가 아니며 필요한 셀프 서명은 허용한다.

## 결정

1. 제작 도구와 생성 앱 모두 Tauri 2 + Rust를 사용한다.
2. Builder, Runtime, Studio를 분리한다. 프로젝트 스키마와 행동 엔진을 공통 Rust 라이브러리로 공유한다.
3. 프로젝트는 선언형 데이터와 리소스다. 프로젝트별 사용자 코드를 컴파일·실행하는 시스템은 초기 범위에 포함하지 않는다.
4. 생성 앱은 각자의 제품 메타데이터·식별자·리소스를 포함하며 제작 도구 설치에 의존하지 않는다.
5. Windows는 공식 서명 없는 배포를 기본으로 하고, macOS는 ad-hoc 서명을 기본으로 설계한다. 공식 인증서·공증 작업을 빌드의 필수 단계로 만들지 않는다.
6. Windows 앱은 Windows에서, macOS 앱은 macOS에서 빌드하는 경로를 우선 제공한다.

## 상세 설계 제안

WebView 화면은 TypeScript + Vite + Canvas 2D로 시작한다. React·Svelte·PixiJS·Rust WASM UI의 도입은 별도 결정이다. 앱 제작자는 Rust나 TypeScript를 수정하지 않고 프로젝트 데이터만 작성한다.

입력은 OS별 네이티브 어댑터를 Rust 인터페이스 뒤에 둔다. 전역 단축키 API를 일반 타이핑 감지로 대체하지 않는다. 입력 패키지의 최종 선택은 초기 기술 검증에서 확정한다.

## 결과와 비용

- Rust 네이티브 코드·도구체인 유지보수와 OS별 WebView 검증이 필요하다.
- 시스템 WebView를 사용한다는 사실만으로 낮은 메모리·전력이 보장되지는 않는다.
- 공식 신뢰 서명이 없으므로 다운로드한 앱의 실행 승인은 별도 사용자 흐름이다. 셀프 서명이 신뢰 경고를 자동으로 해소한다고 가정하지 않는다.
- Tauri를 선택했다는 사실과 제품의 기능·성능이 검증되었다는 사실을 구분한다.

## 구현 전 검증

투명 창·클릭 통과·포커스·입력 권한·DPI 좌표·독립 앱 패키징을 검증한다. 실패하면 우선 해당 어댑터나 창 구현을 수정한다. 프레임워크 변경은 실패 근거와 비용을 기록한 후속 ADR로 결정하며 현재 결정을 조용히 바꾸지 않는다.

공식 문서 근거와 버전 주의사항은 [기술 비교](../technology-evaluation.md)와 [참고 자료](../references.md)에 둔다.
