# 구현 계획

상태: M0~M3 구현·검증 진행, 출시 gate 미완료 / 기준일: 2026-11-07

진행 증거와 미완료 항목은 [개발 검증 기록](validation/2026-11-07-development.md)을 따른다. 지원 OS 실기·외부 설치를 기다리는 동안 독립적인 코어·Builder 작업을 진행하되 M0를 통과한 것으로 표시하지 않는다.

## 1. 개발 순서

**두 OS의 최소 입력·오버레이·앱 패키징·외부 실행(M0) → 스키마와 순수 코어(M1) → 공통 Player(M2) → 운영 가능한 Builder(M3) → Studio(M4)** 순서다. M0는 위험을 검증하는 작은 세로 경로, M3는 전체 P0 계약을 충족하는 제품이다. Studio UI와 캐시 최적화보다 독립 앱 경로를 먼저 증명한다.

일정은 인력·OS별 테스트 기기 확인 후 추정한다. 아래 버전 표기는 계획 이름이며 배포된 릴리스가 아니다.

## 2. M0: OS 기술 검증과 최소 독립 앱 경로

### 작업

- Tauri 2 + Rust의 호환 가능한 코어·API·CLI 버전을 고정한다.
- Windows 11 25H2 x64와 macOS 15 arm64 기준 실제 기기를 확보하고 OS·IME·WebView·전원 조건을 기록한다. 성능 기준은 Windows 4코어/8GB 이상 실기와 M1/8GB급 Apple Silicon 실기로 정한다.
- Windows/macOS에 작은 투명 창·트레이·직접 드래그·설정 전환을 만든다.
- Windows Raw Input·macOS listen-only session tap을 직접 감싼 Rust 어댑터로 일반 사용자 세션의 down/up·modifier·마우스·권한을 검증한다. 캐릭터 앱 포커스 없이 편집기·브라우저·업무 앱에서 원래 입력과 반응이 함께 동작해야 한다.
- 입력 속도 기본 집계, 특정 키·한글 두벌식 키 순서 반응을 작은 fixture로 연결한다. 현재 한/영 모드와 독립적인 패턴 판정을 확인하고 IME 확정 문자열 판독으로 설명하지 않는다.
- 최소 workspace·Player 템플릿으로 서로 다른 두 이름·identifier·아이콘·리소스의 앱을 두 OS에서 각각 패키징한다. macOS는 ad-hoc, Windows는 미서명 사용자 단위 설치다.
- 각 OS의 제작 도구 없는 외부 기기에서 실제 다운로드·설치·전역 반응을 확인한다. macOS OS 실행 승인과 입력 권한은 각각 확인한다. 동시에 두 앱을 실행한다.
- 장치 제거·보안 입력·감지 재개 시 held 초기화, 비활성 창의 포커스, 작업 표시줄/Dock·Space 정책, CSP 적용 가능성을 검증한다.
- DPI/모니터 좌표와 CPU·GPU·메모리 기준선을 기록한다.

### 종료 조건

두 OS에서 핵심 입력·창·권한과 두 앱의 최소 외부 설치 경로를 재현하고 제약·고정 도구 버전·정규 키 지원표를 기록한다. 아직 Windows 기기가 없다면 Mac/mock 결과만으로 완료하지 않는다. OS별 실기 기록은 `docs/validation/`에 추가한다. 현재 개발 환경에서 확인한 부분 증거는 개발 검증 기록에 있으며, 지원 OS 실기·외부 설치 gate는 아직 통과하지 않았다. 프로토타입을 정식 Builder 완료로 표시하지 않는다.

## 3. M1: 스키마와 공통 코어

### 작업

- M0 workspace를 buddy-project/runtime/platform/builder와 공통 renderer 구조로 확장한다. TypeScript + Vite + Canvas 2D를 사용하고 최초 Studio 폼에도 별도 UI 프레임워크를 넣지 않는다.
- Project/Character v1 타입·JSON Schema·validator를 만든다.
- 스키마·자산·경로·프레임 참조·버전 오류 fixture를 만든다.
- 순수 Rust 코어에 모의 단조 시각·이벤트·작업 영역을 주입한다. priority·동률·중단 폐기·쿨다운·반응 종료·walk·held·epoch reset을 검증한다.
- KPS 창·안정화·유휴, keyword 두벌식 변환·Shift·KMP·timeout·키/sequence 동시 후보를 fixture로 검증한다. 입력 이력을 기록하지 않는다.
- Rust 타입에서 JSON Schema·TypeScript DTO를 생성하고 재생성 차이를 CI에서 차단한다.

### 종료 조건

프로젝트 JSON만으로 서로 다른 행동 정의를 로드할 수 있고 잘못된 정의는 빌드 전에 설명 가능한 오류를 반환한다. 사용자 코드를 실행하는 확장 구멍을 만들지 않는다.

## 4. M2: 공통 Player와 미리보기

### 작업

- 다중 이미지·GIF·영역의 공통 Canvas 렌더러와 Runtime 상태 스트림을 연결한다.
- 실제 전역 입력을 동작에 연결하고 원래 앱의 입력이 유지되는지 확인한다.
- 즉시 드래그·설정 배율·모니터 제한·트레이 상태·사용자 설정을 구현한다.
- 드래그 저장·설정·숨김·일시 정지 상태 전환표, 소스별 권한/수신 분리와 fresh-input 재개를 구현한다.
- 권한 거부·절전·장치 제거·보안 입력·채널 재연결·설정 손상/미래 버전·저장 실패 복구를 구현한다. 기본 배치와 세션 이동을 분리한다.
- Rust 동작 deadline·최대 60 Hz 이동·설정 가능한 속도 평가(기본 50 ms), 최대 30 FPS 렌더와 정적 유휴 중단을 연결한다. key·속도·sequence가 다른 앱 작업 중에도 반응해야 한다.
- 창별 command manifest·Rust 진입부 검사·release CSP·자산 scope를 적용하고 금지 호출을 검증한다.
- CLI 미리보기는 공통 Player를 사용한다.

### 종료 조건

샘플 데이터만 바꿔 타이핑과 클릭 캐릭터를 각각 미리 볼 수 있다. 유휴·숨김·종료 시 자원이 정리되고 입력 원문은 로그에 남지 않는다.

## 5. M3: 독립 앱 Builder — 최초 MVP

### 작업

- OS별 CLI 릴리스와 버전 고정 템플릿 팩을 만들고 Player·공통 소스·잠금 파일을 자체 포함한다. 원래 저장소 없는 제작 환경에서 doctor→build를 검증한다.
- 경로·크기 사전 검사→변경 감지 snapshot→snapshot 최종 검증·keyword steps 변환·hash 확정→생성·빌드 경로를 구현한다. 최종 검증 후 원본을 읽지 않는다.
- 도구체인 진단, OS별 빌드, 진행·취소·보고서·기본 의존성 캐시 재사용을 제공한다. 캐시 최적화는 M5에서 하되 올바른 키·격리는 지금 검증한다.
- Windows 사용자 단위 설치 파일과 macOS `.app`/DMG를 생성한다.
- 기본 서명 정책과 선택적인 로컬 셀프 서명 identity 경로를 구현한다.
- 서로 다른 두 프로젝트의 앱 식별자·설정·설치 항목이 분리되도록 한다.
- 설치·권한·키워드 판정 방식·업데이트·제거 안내, SHA256SUMS·라이선스·platformIdentity 보고서를 산출물에 포함한다.

### 종료 조건

**타이핑 고양이와 클릭 마스코트를 공통 소스 수정 없이 빌드해 다른 컴퓨터에서 각각 설치·실행한다.** 제작 도구·원본 프로젝트·Rust·Node가 없어도 동작해야 한다. 공식 인증서·공증 없이 배포 경로를 검증한다.

별도로 원래 소스 checkout 없는 제작 환경에서 배포된 CLI·템플릿 팩·필수 도구체인만으로 두 앱을 빌드한다. P0 전체와 두 앱 동시 실행 N09·업데이트 설정 보존·동작 계약 회귀가 통과해야 M3를 완료한다. M0의 단순 패키징 성공을 재사용하되 새 템플릿/서명/입력 변경 뒤에는 관련 실기를 다시 수행한다.

CLI 계약은 다음과 같다. 현재 new/validate/doctor/preview/build 및 개발용 export-contracts/template-pack/simulate/input-probe를 구현하고 검증 중이다. CLI·미리보기 Player·팩 묶음 생성 경로도 구현했으며, 미리보기의 실제 UI·입력과 제작 도구만 있는 외부 환경의 배포 CLI 검증은 미완료다. npm run player:dev는 개발 실행 경로이며 preview 완료를 대신하지 않는다.

| 명령 | 목적 |
| --- | --- |
| `buddy new` | 프로젝트 뼈대 생성 |
| `buddy validate` | 프로젝트·자산 검증 |
| `buddy preview` | 공통 Runtime 미리보기 |
| `buddy doctor` | OS 하한·고정 Rust/웹 도구·대상 std 진단. 누락 시 JSON 준비 안내와 종료 코드 1 |
| `buddy build` | 프로젝트에서 독립 앱 빌드 |

## 6. M4: Studio GUI

### 작업

- 프로젝트 생성·복제·최근 목록·저장을 제공한다.
- 제품·리소스·애니메이션·속도 구간·특정 키·keyword/layout·변환 steps·move.animation 폼을 만든다. 구간 겹침·동작 가림·실제 텍스트와 무관한 물리 패턴임을 설명한다.
- 웹 모의 입력 미리보기와 빌드된 Player의 실제 전역 입력 검증을 구분한다.
- Builder를 호출해 진행·오류·취소·산출물을 표시한다.
- 저장하지 않은 편집, 외부 파일 변경, 미래 버전 프로젝트를 처리한다.

### 종료 조건

제작자가 Rust/TypeScript를 수정하지 않고 GUI에서 두 프로젝트를 만들고 독립 앱을 내보낸다. Studio 미리보기와 배포 앱이 같은 Runtime·자산·행동 규칙을 사용한다.

## 7. M5: 배포 품질과 지원 확대

M3를 통과한 뒤 캐시 효율·5개 앱 확대 성능·지원 사례를 개선한다. 필수 OS의 설치·성능·다중 모니터·업데이트 검증은 M3 이전에도 필수이며 M5로 미루지 않는다. macOS Intel 지원은 실제 기기 검증 뒤 추가한다. GitHub Actions 원격 빌드는 사용자 추가 요구에 따라 [별도 계약](studio-actions.md)으로 도입했다. 복수 캐릭터·자동 업데이트·레이어/3D는 후속 요구사항과 ADR로 진행한다.

## 8. 주요 위험과 해결 순서

| 위험 | 먼저 할 일 | 대안 |
| --- | --- | --- |
| 전역 입력 권한·누락 | 실제 OS adapter와 배포본으로 검증 | native 구현/패키지 교체, 미지원 키 명시 |
| 투명 창 GPU 부하 | 작은 창, 유휴 중단, 실제 전력 측정 | renderer/창 구현 조정 후 필요하면 후속 ADR |
| 앱이 미리보기와 다르게 동작 | 같은 Runtime과 schema 사용 | 버전/hash를 보고서로 추적 |
| 독립 앱의 설정 충돌 | identifier·잠금·설치 ID를 일관되게 파생 | 빌드 전에 중복 제품 정의 검출 |
| 제작자 도구체인 부담 | doctor와 단계별 오류, GitHub Actions 빌드 | hosted runner 결과와 실제 지원 OS 검증 구분 |
| 배포본 실행 차단 | 다운로드한 파일로 설치 재현 | 해당 정책 환경의 지원 제한을 설명 |
| 프로젝트 형식 변경 | versioning과 fixture·마이그레이션 | 원본 보존·미래 버전 편집 차단 |

## 9. 결정과 실증 기록의 구분

화면 기술·입력 API·OS 하한·identifier 기본 namespace·v1 스키마·동작/상태 계약·Builder 팩 방식은 [ADR 0002](decisions/0002-runtime-and-builder-contracts.md)와 [ADR 0003](decisions/0003-global-typing-reactions.md)에 따라 결정했다. 구현을 기다리는 시험 결과를 미정 제품 요구와 혼동하지 않는다.

M0에서 실제 Tauri/Rust/Node/패키지 매니저 버전·Windows/맥 기기명·WebView·입력 API 한계·실측 예산·외부 설치 결과를 잠금 파일과 validation 기록에 채운다. 목표를 달성하지 못하면 미검증/실패를 기록하고 관련 계약·ADR을 근거와 함께 변경한다. 기기와 측정 결과를 문서상으로 만들어 넣지 않는다.

N03 계측 코드는 native 수신 시각·일회성 반응 시작·렌더러 drawn/error ACK의 상관 처리, 제외/누락 집계와 설정의 진단 JSON 저장까지 구현했다. 30 FPS 시험 fixture와 자동 회귀는 [시험 전략](testing-strategy.md#6-성능-측정-방법)을 따른다. 다음 성능 작업은 지원 OS의 Release 실측이며 내부 main 진입 시간만으로 N04 외부 콜드 스타트를 통과시키지 않는다.

기능·성능 미검증은 구현 과제다. 이 문서에 체크가 없다는 이유로 요구사항을 제외하거나, 문서만 작성한 상태를 제품 구현 완료로 표시하지 않는다.
