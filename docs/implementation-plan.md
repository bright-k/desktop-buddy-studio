# 구현 계획

상태: 미착수 계획 / 기준일: 2026-11-07

## 1. 개발 순서

**프로젝트 데이터 → 공통 Runtime → 독립 앱 빌드 → 외부 기기 실행 → Studio 편집 UI** 순서로 진행한다. 프로젝트를 여러 개 저장하는 UI만 만들고 실제 독립 앱 생성을 뒤로 미루지 않는다.

일정은 인력·OS별 테스트 기기 확인 후 추정한다. 아래 버전 표기는 계획 이름이며 배포된 릴리스가 아니다.

## 2. M0: OS 기술 검증

### 작업

- Tauri 2 + Rust의 호환 가능한 코어·API·CLI 버전을 고정한다.
- Windows/macOS에 작은 투명 창·트레이·전체 클릭 통과·편집 전환을 만든다.
- Rust 입력 어댑터로 일반 사용자 세션의 key down/up·마우스·권한 흐름을 검증한다.
- macOS ad-hoc 배포본을 다른 컴퓨터에서 열어 OS 실행 승인과 입력 권한을 각각 확인한다.
- DPI/모니터 좌표와 CPU·GPU·메모리 기준선을 기록한다.

### 종료 조건

두 OS에서 핵심 동작과 권한 흐름을 재현하고 제약을 기록한다. 아직 Windows 기기가 없다면 Mac 결과와 mock 테스트만으로 Windows 완료를 표시하지 않는다. Tauri는 선택한 기반이며 문제는 먼저 플랫폼 계층에서 해결한다.

## 3. M1: 스키마와 공통 코어

### 작업

- Rust workspace와 웹 패키지 구조를 구성한다.
- Project/Character v1 타입·JSON Schema·validator를 만든다.
- 스키마·자산·경로·프레임 참조·버전 오류 fixture를 만든다.
- 모의 입력으로 priority·쿨다운·held 이동·epoch reset을 검증한다.
- TypeScript DTO를 Rust와 맞추는 생성/검사 경로를 정한다.

### 종료 조건

프로젝트 JSON만으로 서로 다른 행동 정의를 로드할 수 있고 잘못된 정의는 빌드 전에 설명 가능한 오류를 반환한다. 사용자 코드를 실행하는 확장 구멍을 만들지 않는다.

## 4. M2: 공통 Player와 미리보기

### 작업

- PNG 시트 Canvas 렌더러와 Runtime 상태 스트림을 연결한다.
- 실제 전역 입력을 동작에 연결하고 원래 앱의 입력이 유지되는지 확인한다.
- 위치·배율·모니터 제한·클릭 통과·편집 모드·트레이·사용자 설정을 구현한다.
- 권한 거부·절전·채널 재연결·입력 중단의 복구 경로를 구현한다.
- CLI 미리보기는 공통 Player를 사용한다.

### 종료 조건

샘플 데이터만 바꿔 타이핑과 클릭 캐릭터를 각각 미리 볼 수 있다. 유휴·숨김·종료 시 자원이 정리되고 입력 원문은 로그에 남지 않는다.

## 5. M3: 독립 앱 Builder — 최초 MVP

### 작업

- 고정된 Player 템플릿에 프로젝트 메타데이터·아이콘·리소스를 반영한다.
- 도구체인 진단, OS별 빌드, 진행·취소·캐시·보고서 기능을 만든다.
- Windows 사용자 단위 설치 파일과 macOS `.app`/DMG를 생성한다.
- 기본 서명 정책과 선택적인 로컬 셀프 서명 identity 경로를 구현한다.
- 서로 다른 두 프로젝트의 앱 식별자·설정·설치 항목이 분리되도록 한다.

### 종료 조건

**타이핑 고양이와 클릭 마스코트를 공통 소스 수정 없이 빌드해 다른 컴퓨터에서 각각 설치·실행한다.** 제작 도구·원본 프로젝트·Rust·Node가 없어도 동작해야 한다. 공식 인증서·공증 없이 배포 경로를 검증한다.

이 단계의 CLI 명령 이름 제안은 다음과 같다. 아직 실행 가능한 명령이 아니다.

| 명령 | 목적 |
| --- | --- |
| `buddy new` | 프로젝트 뼈대 생성 |
| `buddy validate` | 프로젝트·자산 검증 |
| `buddy preview` | 공통 Runtime 미리보기 |
| `buddy doctor` | 빌드 환경·target 지원 진단 |
| `buddy build` | 프로젝트에서 독립 앱 빌드 |

## 6. M4: Studio GUI

### 작업

- 프로젝트 생성·복제·최근 목록·저장을 제공한다.
- 제품 메타데이터, 리소스, 애니메이션, 입력 매핑 폼을 만든다.
- 모의 입력 미리보기와 사용자가 켜는 실제 입력 미리보기를 구분한다.
- Builder를 호출해 진행·오류·취소·산출물을 표시한다.
- 저장하지 않은 편집, 외부 파일 변경, 미래 버전 프로젝트를 처리한다.

### 종료 조건

제작자가 Rust/TypeScript를 수정하지 않고 GUI에서 두 프로젝트를 만들고 독립 앱을 내보낸다. Studio 미리보기와 배포 앱이 같은 Runtime·자산·행동 규칙을 사용한다.

## 7. M5: 배포 품질과 지원 확대

필수 OS의 설치 안내·성능·다중 모니터·업데이트 보존을 반복 검증한다. macOS Intel 지원은 실제 기기 검증이 완료된 뒤 추가한다. 원격 빌드·복수 캐릭터·자동 업데이트·레이어/3D는 별도 요구사항과 ADR로 진행한다.

## 8. 주요 위험과 해결 순서

| 위험 | 먼저 할 일 | 대안 |
| --- | --- | --- |
| 전역 입력 권한·누락 | 실제 OS adapter와 배포본으로 검증 | native 구현/패키지 교체, 미지원 키 명시 |
| 투명 창 GPU 부하 | 작은 창, 유휴 중단, 실제 전력 측정 | renderer/창 구현 조정 후 필요하면 후속 ADR |
| 앱이 미리보기와 다르게 동작 | 같은 Runtime과 schema 사용 | 버전/hash를 보고서로 추적 |
| 독립 앱의 설정 충돌 | identifier·잠금·설치 ID를 일관되게 파생 | 빌드 전에 중복 제품 정의 검출 |
| 제작자 도구체인 부담 | doctor와 단계별 오류 | 후속 버전에서 OS별 원격 빌드 검토 |
| 배포본 실행 차단 | 다운로드한 파일로 설치 재현 | 해당 정책 환경의 지원 제한을 설명 |
| 프로젝트 형식 변경 | versioning과 fixture·마이그레이션 | 원본 보존·미래 버전 편집 차단 |

## 9. 첫 구현 전에 확정할 상세 항목

- 화면용 TypeScript/Vite 채택과 Studio UI 프레임워크 필요 여부
- 플랫폼 입력 어댑터의 crate 또는 직접 구현 범위
- 최초 지원 OS 하한과 실제 테스트 장비
- 프로젝트 스키마의 최종 필드·제한과 제품 identifier 기본 namespace
- Runtime 성능 예산을 검증할 기준 기기

기능·성능 미검증은 구현 과제다. 이 문서에 체크가 없다는 이유로 요구사항을 제외하거나, 문서만 작성한 상태를 제품 구현 완료로 표시하지 않는다.
